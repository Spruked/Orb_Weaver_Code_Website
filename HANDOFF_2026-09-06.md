## Product scope clarified today

Code Weaver is **not a VS Code monitor**. VS Code is only the first environment adapter.

The broader developer-activity model must support three identity classes:

1. **Desktop editor / IDE windows**
2. **CLI / agent sessions**
3. **Application / service processes**

Each activity identity can have its own optional widget/view. Usage evidence may be linked to an activity identity only when the correlation is defensible. An open editor or a running process is never, by itself, proof that it consumed API tokens.

### Environment views

The existing dashboard is suitable as the VS Code-specific environment view. Additional environment adapters/views should eventually cover, where observable:

- Cursor
- JetBrains IDE family
- Zed
- Windsurf
- Visual Studio
- Neovim / terminal editors
- GitHub Codespaces / remote VS Code
- terminal and CLI agents
- Docker / WSL application processes
- other developer environments through future adapters

Automatic desktop discovery should cover editors visible on the current Windows/WSL machine. Terminal, container, remote, and headless tools should use explicit registration and/or usage-reporting hooks where automatic attribution would be unreliable.

## Provider model

Each AI provider gets its **own provider window**, separate from environment windows.

Initial provider order:

1. OpenAI / GPT / Codex
2. Anthropic / Claude
3. Google / Gemini
4. xAI / Grok

The architecture must be adapter-based so additional providers can be added without redesigning the evidence ledger or dashboard.

Provider windows aggregate that provider across every observable environment: IDEs, CLIs, apps, scripts, Windows processes, WSL processes, containers, and services.

Examples:

- OpenAI view: Codex in VS Code + Codex CLI + OpenAI API usage from Dandy, Orb Weaver, scripts, services, etc.
- Anthropic view: Claude Code + Claude in supported editors + Anthropic API calls.
- Gemini view: Gemini CLI/editor integrations + Gemini API calls.
- xAI view: Grok tooling + xAI API calls.

## Global control-plane view

Above the environment and provider windows, Code Weaver should eventually provide a Global view that answers:

- Which providers are active?
- Which developer environments are active?
- Where are tokens being consumed?
- What is subscription quota state?
- What API usage/cost is accumulating?
- Which usage is attributed versus unassigned?
- Which evidence sources are healthy, stale, unavailable, derived, inferred, or observed?

Expected drill-down direction:

`Global -> Provider -> Application/Environment -> Workspace/Session -> Request/Turn`
